# openEagle 开发指南

## 1. 环境要求

- Node.js（建议使用 `corepack` + `pnpm@10.7.0`）
- Python `>=3.12`
- `uv`（用于后端依赖与构建）
- Rust / Cargo（Tauri 开发）

## 2. 本地启动

```powershell
corepack enable
corepack prepare pnpm@10.7.0 --activate
pnpm install
uv sync --project .\backend
pnpm tauri:dev
```

## 3. 编码与文件规范（强约束）

- 所有文件读写必须使用 `UTF-8`（无 BOM）。
- 在 Windows 下执行写文件前，先确认控制台编码：

```powershell
chcp 65001
```

- 禁止使用默认编码、GBK、ANSI。
- 如果发现中文乱码，先确认正确原文来源（历史版本/上下文）后再改，不能“猜测修复”。

## 4. 关键架构

### 4.1 进程与连接

- Tauri Rust 启动 Python sidecar。
- 后端启动后输出握手日志：`[AGENT_READY] WS_PORT: <port>`。
- 前端建立 `ws://127.0.0.1:<port>/ws`。

### 4.2 桌面执行流程（内部 `solo` 协议）

1. 前端或 IM 入口发送普通消息到 `client:send_message` / `AgentRuntime`。
2. main agent 判断任务需要桌面视觉操作时，路由到内部 `start_solo` worker。
3. 后端截图、VL 决策、下发 `server:solo_step`。
4. 执行动作并通过 `server:trace`、`server:solo_status` 回传。
5. 遇到危险动作进入 `server:solo_confirmation_required`。

### 4.3 Main/Sub-Agent Runtime

- 普通 `client:send_message` 与 IM 文本消息先进入 `AgentRuntime`。
- `AgentRouter` 负责输出路由决策：直接回答、创建 worker、复用 worker、启动桌面执行 worker 或控制当前桌面执行。
- Router prompt 以原则和 worker 能力声明为主，不用关键词清单堆规则。`clarify` 只用于不可撤销且缺失信息会导致完全错误结果的场景；`preferred_mode=solo` 只在桌面状态感知或 GUI 操作任务上优先生效。
- `answer_directly` 的最终回复来自路由 JSON 的 `answer` 字段；`user_visible_summary` 必须是第一人称口语，不要暴露“交给某个 worker”这类系统日志语气。
- `SubAgentManager` 使用内部 scoped conversation id：`<conversation_id>:worker:<worker_id>`，让 worker 上下文保持干净。
- `general` / `research` worker 可保守并发；`coding` 与写入类任务串行；桌面执行 worker 全局单实例。
- 前端通过 `server:trace` 展示 `kind="agent"` 的 main-router 与 worker 摘要；工具确认仍沿用原有 confirmation 机制。

### 4.4 显示器选择与预览

- 前端可发送 `client:list_solo_displays` 获取显示器列表与实时预览。
- 设置中的 `solo.preferredDisplayIndex` 会通过 `client:update_settings` 同步到后端。
- 后续桌面执行截图按该显示器执行。

### 4.5 远程 IM 入口

- 后端 `IMBridge` 负责飞书、Telegram 与微信的消息接入、白名单校验、会话绑定和回复路由。
- 飞书使用长连接机器人：`feishu.appId` / `feishu.appSecret` 用于连接，`allowedOpenIds` 与 `allowedChatIds` 用于放行用户或会话。
- Telegram 使用 Bot API 长轮询：`telegram.botToken` 用于连接，`allowedUserIds` 与 `allowedChatIds` 用于放行用户或会话。
- 白名单为空时拒绝所有远程来源；最近被拦截的 ID 会通过 `server:im_status` 回到设置页，便于复制配置。
- 远程普通文本先进入 main agent，由 main agent 决定直接回复、调用工具或调度桌面执行；`/solo <任务>` 只用于显式优先调度桌面执行。`/pause`、`/resume`、`/stop`、`/allow`、`/reject` 用于控制当前远程桌面执行。
- 飞书 SDK 的 WebSocket 客户端使用模块级 asyncio loop，必须绑定到独立线程中的专用 loop，避免复用 FastAPI 主事件循环。

### 4.6 定时任务

- 后端启动时初始化 `.open-eagle/scheduler.db` 并启动 `SchedulerService`。
- agent 通过默认工具 `create_scheduled_task(name, prompt, schedule_expr, worker_kind)` 创建任务；`prompt` 是到点后执行的完整指令，创建任务时不要立即执行该指令。
- 当前调度表达式使用 cron 格式：`分 时 日 月 周`，例如每天 20:00 为 `0 20 * * *`。
- WebSocket 支持：
  - `client:scheduled_task_list`
  - `client:scheduled_task_create`
  - `client:scheduled_task_update`
  - `client:scheduled_task_delete`
  - `client:scheduled_task_history`
- 前端设置页负责展示、创建、编辑、启停、删除任务，并拉取执行历史。执行结果通过 `server:scheduled_task_executed` 追加到会话。
- 任务执行仍走 `SubAgentManager` 和 worker kind，不绕过原有 worker 模型。后续若接入更严格的权限模型，应把 scheduled run 的自动确认策略单独收紧。

### 4.7 长期记忆

- 后端启动时初始化 `.open-eagle/memory.db`，核心代码在 `backend/app/memory`。
- WebSocket 协议：
  - `client:memory_get`
  - `client:memory_save`
  - `client:memory_ingest_snapshot`
  - `server:memory_state`
  - `server:memory_updated`
- `MemoryService.record_turn()` 在用户回合完成后追加原始事件；`distill_event()` 有可用文本模型时异步蒸馏画像、笔记和 Agent 旁注。
- `MemoryService.prompt_context()` 只输出精简后的用户画像、活跃笔记和 Soul 摘要，不把原始事件直接塞进每次 prompt。
- 用户手动保存的画像、笔记和 Soul core 优先级最高；自动蒸馏不能覆盖手动画像，也不能更新或归档手动笔记。
- `default_tools` 暴露 `get_memory_state`、`save_memory_note`、`update_memory_note`、`delete_memory_note`、`save_user_profile`、`save_soul_core`、`save_agent_side_notes`。记忆类请求必须走这些工具或 WebSocket memory API，不要在项目根目录创建 `.txt` / `.md` 记忆文件。
- 前端 Settings -> Memory 只渲染活跃用户笔记；删除笔记会写成归档状态并从列表隐藏，审计记录和数据库留痕仍然保留。
- 原始事件和快照必须走 `sanitize_text()` / 结构化 payload 清洗，避免保存明显密钥、token、密码等敏感内容。

### 4.8 上下文整理

- 配置入口为 `AppConfig.context`，前端设置页会通过 `client:update_settings` 同步：
  - `maxInputTokens`
  - `preserveRecentMessages`
  - `imIdleCleanupMinutes`
  - `toolMessageMode`
  - `aiSummaryEnabled`
  - `snapshotOnCompaction`
  - `summaryCharLimit`
- `backend/app/context_cleanup.py` 是唯一的消息整理实现；新增 provider 时应复用这里的函数，不要复制一套规则。
- 触发整理后必须保留 system 消息和最近 N 条消息，只处理中间消息。如果最近消息包含 Anthropic `tool_result`，需要同时保护前一条配对的 `tool_use`。
- AI 摘要前必须先预清理工具消息，避免把大段工具输出交给摘要模型。工具消息按配置占位或移除，结构化工具块保留协议形状。
- 压缩前可通过 `context_compaction` snapshot 写入长期记忆；这条路径和前端本地存储裁剪的 `client:memory_ingest_snapshot` 共享同一个记忆摄取思路。
- 当前自定义 AI 中段摘要接在 Anthropic provider，因为该 provider 能看到完整 message/tool loop；Agno 路径主要依赖自身 `compress_tool_results` 与 history 参数。

### 4.9 桌面执行稳定性策略

- `action_signature` 用于判断真正重复的动作，避免把不同坐标的点击误判为同一动作。
- 桌面执行 step outcome 分为 `success` / `no_op` / `uncertain` / `failed`，恢复早于暂停。
- recovery mode 只给模型换路线提示，不接管模型每一步；进入 recovery mode 后会临时抑制 batch actions。
- `open_url`、点击、双击、`press_keys` 会在动作后做短暂截图稳定采样，尽量把页面加载完成后的画面交给下一轮决策。
- 动作参数格式错误、工具执行失败等可修复问题会写入当前 agent 历史，让 agent 重新决策；连续失败达到阈值才暂停给用户。
- 完成或暂停时写入 `stability_summary`，用于后续定位卡住、重复动作和截图无变化问题。

## 5. 图片显示说明

为避免 `asset.localhost` 在部分机器上访问临时目录出现 `404`，项目增加了 Rust 命令 `read_image_data_url`：

- 前端优先将本地截图路径转换为 `data:image/...;base64` 再渲染。
- 该机制用于设置页显示器预览以及对话中的桌面执行截图预览。
