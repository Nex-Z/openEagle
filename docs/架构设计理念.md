# 架构设计理念

## 1. 混合架构

- 后端使用 Python（FastAPI + WebSocket）承载 Agent 推理、桌面执行编排与业务协议。
- 桌面壳使用 Electron（Node.js）负责进程托管与本地系统能力。
- 前端使用 React + TypeScript 负责对话界面、设置中心、状态可视化。

## 2. 后端部署模型

- 开发环境：由 Electron 启动本地 Python 环境运行 `app.main`。
- 生产环境：Python 后端可通过 `PyInstaller` 打包为 sidecar 可执行文件。

## 3. 动态端口握手

1. Python 后端以随机端口启动（`port=0`）。
2. 启动成功后输出握手日志：`[AGENT_READY] WS_PORT: <port>`。
3. Electron 主进程监听 sidecar 输出，解析端口并通过 IPC 发布给前端。
4. 前端连接 `ws://127.0.0.1:<port>/ws`。

这样可以避免端口冲突，提升多实例与本地环境兼容性。

## 4. 生命周期接管

- 开发启动由 `scripts/electron-dev.cjs` 负责：先编译 Electron 主进程并启动 Vite，再拉起 Electron 桌面壳。
- Electron 统一管理 sidecar 启停。
- 主窗口退出时，Electron 主动终止后端子进程，避免孤儿进程。
- 连接断开时前端执行自动重连策略并回显状态。

## 5. 桌面执行设计原则

- 模型只做“决策”，执行由本地工具层负责。
- 所有关键步骤通过 `server:solo_status / step / trace` 回传，保证可追踪。
- 危险动作进入显式确认流程，减少误操作风险。
- 自动暂停机制用于防止死循环（如连续重复动作）。
- 稳定性策略保持温和：用 action signature、no-op/uncertain/failed 分类和 recovery mode 提醒模型换路线，但不把桌面执行改成固定脚本。
- 可修复的坏输出或执行错误先反馈给当前 agent 重新决策，连续失败才暂停给用户判断。

## 6. Main/Sub-Agent 分层

- 所有普通用户消息先进入 MainAgent。MainAgent 是用户面对的 leader，负责意图理解、最近对话承接、直接回复、澄清、派工和最终汇总；worker 只是被委派的执行者。
- MainAgent 的内部决策步骤以原则和能力声明为核心，不用关键词清单驱动路由。模型先结合当前消息、最近对话、长期记忆和 worker 状态判断任务性质、时间意图、所需能力和复用机会，再输出结构化决策 JSON。
- `clarify` 只用于缺失信息会导致不可撤销且完全错误结果的场景；可合理假设或可修正的不确定性直接交给 worker 推进。
- `preferred_mode=solo` 只在任务涉及桌面状态感知或 GUI 操作时优先启动桌面执行；纯检索和代码任务仍按实际能力路由。
- `answer_directly` 的直接回复由 MainAgent 内部决策写入 `answer` 字段，避免再走一层泛化直接回复模型；`user_visible_summary` 使用第一人称口语，避免把内部 worker 调度暴露成系统日志。
- sub-agent 使用干净的内部 conversation id 执行任务，完成后只回传摘要、证据和结果，减少主会话上下文污染。
- worker 分为 `general`、`coding`、`research`、`solo`；其中 `solo` 是桌面执行 worker 的内部标识。只读 worker 可保守并发，写入类 worker 与桌面执行串行。
- 桌面执行通过 `SoloWorkerAdapter` 纳入统一调度，但视觉观察、执行、恢复和验证仍由桌面执行内核自己负责。
- 前端以 `server:agent_progress` 展示 MainAgent 在委派前的一句话进展说明，以 `server:trace` 展示 worker 摘要、工具调用和对用户有意义的记忆操作，用户可展开查看细节，但默认不刷屏。MainAgent 的内部决策 JSON 不进入 Run calls UI。

## 7. 长期记忆与上下文整理

- 记忆子系统位于 `backend/app/memory`，使用 `.open-eagle/memory.db` 持久化，按单一用户设计。
- 记忆分四层：用户画像、用户笔记、Soul、原始记忆事件。原始事件追加写入，不直接注入普通 prompt。
- Prompt 注入采用 V2 检索：有界用户画像摘要、压缩 Soul 摘要、Agent 旁注常驻；用户笔记按当前请求做轻量相关性召回，只注入 active top-k。完整记忆通过 `get_memory_state` 工具按需读取。
- 用户手动编辑的画像、笔记和 Soul core 优先级最高；Agent 只能自动维护用户画像、自动笔记和 Agent 旁注。
- 记忆读取、保存、更新和删除以系统默认工具暴露给 main/worker/solo：`get_memory_state`、`save_memory_note`、`update_memory_note`、`delete_memory_note`、`save_user_profile`、`save_soul_core`、`save_agent_side_notes`。运行时记忆写入 memory 数据库，不在项目根目录生成记忆文件。
- 客户端设置页只显示活跃用户笔记；删除笔记采用归档语义，从列表隐藏但保留审计和后续追踪能力。
- 每个用户回合完成后会记录原始事件；有可用文本模型时异步蒸馏，不阻塞正常回复。
- 上下文整理由 `backend/app/context_cleanup.py` 统一实现，按估算 token 阈值触发，保留 system 与最近 N 条消息，只处理中间消息。
- 中间段进入 AI 摘要前会先预清理工具消息：工具结果占位或移除，结构化 `tool_use/tool_result` 保留协议形状但压缩内容，避免摘要模型浪费 token。
- 压缩前可将预清理后的中间段作为 `context_compaction` 快照写入长期记忆；AI 摘要失败时回退到规则型截断/占位。
- 远程 IM 支持按静默时间提示开启新上下文窗口，用长期记忆和最近消息承接，而不是依赖过旧中段上下文。

## 8. 远程 IM 接入

- `IMBridge` 位于后端内部，将飞书、Telegram 的外部消息转换成普通 openEagle 会话事件。
- 每个远程会话会生成稳定的 `im_<channel>_<hash>` 会话 ID，前端仍通过现有 WebSocket Envelope 协议接收消息、桌面执行状态和确认请求。
- 飞书按 `open_id` 或 `chat_id` 白名单放行；Telegram 按 `user_id` 或 `chat_id` 白名单放行；微信按配置的用户或会话白名单放行。任一命中即可进入会话，白名单为空则拒绝全部远程来源。
- 远程普通文本先进入 main agent，由 main agent 判断是直接对话、调用工具还是调度桌面执行；`/solo` 仅用于显式优先调度桌面执行。
- 远程会话静默超过 `context.imIdleCleanupMinutes` 后，下一轮消息会携带上下文整理提示，避免模型继续依赖旧中段消息。
- 飞书长连接 SDK 自带 asyncio loop 管理，后端将其隔离在独立线程与专用 loop 中，避免和 FastAPI 主事件循环互相阻塞。

## 9. 定时任务

- 非即时的时间意图由 MainAgent 视为持久化任务创建请求，交给 `general` worker 使用 `create_scheduled_task` 工具落库，而不是立即执行任务内容。
- 定时任务使用 `backend/app/scheduler` 模块管理：`models.py` 定义任务与执行记录，`store.py` 负责 SQLite 持久化，`service.py` 负责 APScheduler 调度与 worker 执行，`tools.py` 提供 agent 工具入口。
- 数据库位于 `.open-eagle/scheduler.db`，包含 `scheduled_tasks` 与 `scheduled_task_executions` 两张表，用于保存任务配置、下次执行时间、最近执行时间和历史结果。
- WebSocket 协议提供 `client:scheduled_task_list/create/update/delete/history` 与对应 `server:scheduled_*` 事件；前端设置页可管理任务并查看执行历史。
- 到点执行时，scheduler 会构造 `delegate_new` 决策并按任务配置的 worker kind 运行。执行结果通过 `server:scheduled_task_executed` 回到原会话，保持和普通 worker 汇报一致的用户体验。

## 10. 显示器与截图策略

- 支持从设置页选择桌面执行显示器（`preferredDisplayIndex`）。
- 后端按该设置执行截图与坐标映射。
- 对可能触发页面加载的动作做动作后截图稳定采样，避免将过早的 loading 帧作为下一轮模型输入。
- 提供实时显示器预览用于选择校验。
- 为规避 `asset://` 在部分机器对临时目录的访问限制，前端支持通过 Electron IPC 读取图片并渲染为 data URL。

## 11. Electron 应用资源

- 应用图标在 `build/icon.png` 与 `build/icon.ico` 中维护。
- 开发窗口通过 `BrowserWindow.icon` 使用该资源；Windows 打包通过 `electron-builder.yml` 的 `win.icon` 使用 `build/icon.ico`。
- 图标生成脚本是 `scripts/generate-icons.cjs`，需要调整品牌图形时优先改脚本再重新生成资源。
